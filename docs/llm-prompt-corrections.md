# Коррекции запросов к LLM

## Текущие персональные настройки

В админской панели откройте «Анализ и рабочий день» → «Модель» →
«Персональные коррекции запросов к модели». Для каждого рабочего типа запроса
есть отдельное текстовое поле. Скопируйте рекомендованное по обращению правило
в подходящее поле и сохраните настройки. Пустое поле не меняет запрос.

Коррекция добавляется после основного системного промпта только при вызове
выбранного типа. Основной промпт, входные данные и JSON-схема ответа остаются
в коде. Изменение действует на новые вызовы; уже полученные результаты не
пересчитываются. Для проверки влияния на разбор писем можно повторно запустить
регрессионный набор с аналогичным правилом в его отдельном контракте.

Настройки хранятся в `settings.llm_prompt_corrections` и могут быть заданы в
`secretary-config.json`. Поддерживаются ключи `message_analysis`,
`task_extraction`, `delegation_analysis`, `meeting_delegations`,
`email_thread_match`, `meeting_topic_match`, `archive_reference_selection`,
`archive_answer`, `task_formalization`, `due_date_resolution` и
`diagnostic_redaction`. Максимум — 4000 символов на поле. Проверочный запрос
подключения модели не использует эти коррекции.


## Требования к временным коррекциям из поддержки

История исходных запросов для разбора писем и результатов встреч хранится в
корневом `llm_manifest.json`. Каждая запись содержит версию серверного выпуска,
точный системный запрос, схему ответа и хеши. Доступные прошлые версии
восстановлены из Git и помечены `historical_source`; это не утверждение о
фактической публикации артефакта. Новая запись сначала имеет состояние `planned`.
После изменения запроса сначала задают версию готовящегося выпуска в корневом
`version`, затем выполняют `python3 scripts/update_llm_manifest.py`.
Скрипт добавляет запись только при изменении LLM-запроса или схемы ответа и не
переписывает снимки предыдущих версий, включая ещё не опубликованные. Выпуск
без таких изменений использует последний снимок с версией не выше текущей;
`--check` сверяет с ним серверный код и не требует новой записи на каждый выпуск.
`--finalize` используют только после проверки фактического выпуска, для которого
есть отдельный снимок. Обезличивание и прочие LLM-запросы, не связанные с
обработкой сообщений, в этот манифест не входят.

Дата согласования: 2026-09-26. Реализованы серверная сверка временных
коррекций с манифестом установленного релиза, отдельное хранение статусов и
истории, а также приём структурированных рекомендаций от gateway в обращениях.
В веб-интерфейсе пользователь может применить или отклонить рекомендацию;
до явного применения запрос к LLM не меняется. Последующая ревизия с новым
текстом приостанавливает старое правило до нового согласия. Если кандидат в системную
проблему заменяет прежнее индивидуальное предложение, оно исключается из
применимых коррекций. Мобильный интерфейс этого действия ещё не добавлен.

Индивидуальная коррекция имеет `scope=individual` и не получает `issue_id`.
Если предполагается исправление для всех пользователей, gateway резервирует
устойчивый `issue_id` уже для кандидата. Полную общесистемную проблему с
применимой коррекцией gateway сразу принимает в бэклог; неполный случай
остаётся на проверку оператора. После принятия
`issue_id` заносится в реестр `llm_system_issues`; связанная коррекция имеет
`scope=systemic`. База запрещает указать `issue_id` индивидуальной коррекции
или сослаться на неизвестную системную проблему. Даже при наличии исправления
в манифесте автоматическое отключение допускается только для системной
коррекции, чья проблема остаётся в признанном бэклоге.

Манифест поставляется внутри серверного бинарника в
`backend/internal/server/llm_fix_manifest.json`. Его `release_version` должен
совпадать с корневым `version`; это проверяет серверный тест. В `fixes` включают
только фактически реализованные и проверенные исправления. Для каждого
исправления обязательны `fix_id`, `issue_id`, `request_type`,
`template_revision` затронутого старого запроса и `fixed_version` первого
выпуска с исправлением; `model` ограничивает исправление конкретной моделью.
Манифест каждого выпуска перечисляет все исправления, которые продолжают
работать в установленном коде, включая перенесённые из предыдущих релизов.
При переносе `fixed_version` сохраняется. Манифест встроен в серверный бинарник
для Docker, macOS и Windows; внешняя копия на gateway не подтверждает установку.
Пустой список `fixes` означает, что выпуск не отключает временные коррекции.
При несовпадении версии или повреждении манифеста исправление не считается
установленным. Сверка выполняется до добавления временного правила в новый
LLM-запрос, а также при открытии настроек.

### COR-01. Разделение постоянных и временных правил

- Постоянные персональные инструкции остаются в `settings.llm_prompt_corrections`.
  Обновление приложения не должно изменять или удалять их.
- Временные коррекции поддержки хранятся отдельными структурированными записями
  на персональном сервере, который формирует LLM-запросы. Они не дописываются
  автоматически в общее текстовое поле постоянных инструкций.
- Для каждого вызова сервер использует постоянные инструкции и только активные,
  применимые временные коррекции выбранного типа запроса. Порядок применения
  должен быть детерминированным; противоречащие правила нельзя молча объединять.
- Коррекции не могут отменять ограничения безопасности, правила обезличивания,
  контракт и JSON-схему ответа. Изменение влияет только на новые вызовы;
  пересчёт существующих результатов требует отдельного действия пользователя.

### COR-02. Формат рекомендации и хранение

Ответ поддержки через API должен содержать структурированную рекомендацию:

- `correction_id` — стабильный идентификатор, `revision` — версия рекомендации;
- `report_id` — исходное обращение; `scope` указывает `individual` или
  `systemic`. В применяемой рекомендации `issue_id` присутствует только для
  признанной системной проблемы, принятой в бэклог исправлений; предложение
  для кандидата содержит зарезервированный `issue_id` отдельно;
- `request_type` — поддерживаемый ключ типа LLM-запроса;
- `text` — точный текст правила, `reason` — объяснение его назначения;
- `applicability` — затронутый компонент и диапазон его версий, идентификатор
  и версия шаблона запроса, ограничения по модели, если проблема зависит от неё;
- ожидаемый результат и пример проверки рекомендации.

Локальная запись дополнительно хранит статус, время предложения и применения,
источник рекомендации, историю переходов, причину отключения и идентификатор
установленного исправления. Формат API версионируется. Неизвестные типы запросов,
некорректные условия применимости и превышение допустимого размера отклоняются.
Повторная доставка одной версии рекомендации не создаёт дубль и не включает
коррекцию, которую пользователь уже отключил. Новая версия с другим текстом
требует повторного просмотра и применения. Переклассификация того же
применённого текста в системную коррекцию сохраняет согласие и добавляет `issue_id`.

### COR-03. Работа пользователя с коррекцией

- В обращении и на странице настроек показываются текст, назначение,
  область применимости и действие «Применить временную коррекцию».
- Ответ поддержки может содержать предлагаемую коррекцию и точное место её
  применения: тип LLM-запроса и соответствующий раздел настроек. Пользователь
  видит предложение вместе с ответом поддержки, до применения.
- После явного согласия пользователя приложение само сохраняет коррекцию
  в нужном месте через авторизованный API его персонального сервера, без ручного
  копирования текста. Место определяется разрешённым `request_type`, а не
  произвольным путём или командой из ответа поддержки. Сервер повторно проверяет
  применимость, права и конфликты непосредственно перед сохранением.
- Без согласия, при отказе или закрытии предложения настройки не меняются.
  После успешного применения показываются результат и место применения;
  при ошибке предложение остаётся доступным для безопасного повтора.
- Пользователь видит активные коррекции, может отключить их и проверить
  ожидаемый результат. Выдача или применение рекомендации сами по себе
  не означают, что обращение решено.
- Редактирование текста создаёт персональный вариант с сохранением связи
  с исходной рекомендацией. После выпуска исправления такой вариант нельзя
  автоматически удалить целиком: нужно предложить отдельно сохранить
  персональную часть и отключить временную. До решения показывается состояние
  «Требует проверки»; если правило уже неприменимо, оно не включается в запрос.
- Ранее вручную вставленные фрагменты нельзя автоматически находить и удалять
  по совпадению текста. Их перенос в управляемую коррекцию требует подтверждения.

### COR-04. Связь с очередью исправлений и релизом

- При создании системного кандидата gateway резервирует устойчивый `issue_id`.
  Только после признания проблемы и включения её в бэклог этот ID можно
  использовать в применяемой временной коррекции и требовании к постоянному
  исправлению. Индивидуальная
  коррекция не получает `issue_id` и не отключается релизным исправлением.
- В релиз включается манифест фактически реализованных и проверенных исправлений:
  идентификаторы исправлений и проблем, компонент, версия выпуска, условия
  применимости по шаблону запроса и модели, если они существенны.
- Наличие требования в очереди, его включение в план или статус обращения
  не являются основанием отключать коррекцию. Основание — применимое исправление
  в фактически установленном компоненте для признанной системной проблемы
  из бэклога.
- Манифест поставляется вместе с доверенным пакетом обновления и доступен локально.
  Текст ответа LLM или произвольное поле входящего обращения не может выступать
  подтверждением установки исправления.

### COR-05. Отключение после обновления

- После успешного обновления и при запуске сервер сверяет временные коррекции
  с манифестом установленной версии и текущей конфигурацией модели и шаблона.
  Сверка повторяется при изменении этих параметров.
- Если связанное исправление установлено и применимо к признанной системной
  проблеме из бэклога, неизменённая временная коррекция автоматически
  исключается из новых LLM-запросов. Проверка должна
  завершиться до формирования первого запроса с новой конфигурацией.
- Запись не удаляется: она получает статус «Отключена исправлением», причину,
  версию компонента и время перехода. Пользователь видит уведомление
  «Коррекция отключена: исправлено в версии X» и историю в настройках.
- Обновление только Android/iOS-клиента не отключает коррекцию серверного
  LLM-запроса, если соответствующий серверный компонент не обновлён.
- Если манифест отсутствует или не подтверждает исправление, нельзя считать
  проблему решённой только по увеличению номера версии. Коррекция продолжает
  действовать лишь в пределах объявленных условий применимости; иначе она
  исключается из запросов со статусом «Требует проверки», а не «Исправлено».
- Сверка идемпотентна. При сбое установки или откате учитывается фактически
  работающая версия, а не версия скачанного пакета.

### COR-06. Откат и ручное отключение

При откате сервер пересчитывает применимость. Неизменённая коррекция, ранее
принятая пользователем и отключённая только установленным исправлением,
автоматически возобновляется, если ошибка снова затрагивает установленную
конфигурацию. Пользователь получает уведомление. Ручное отключение сохраняет
приоритет: такую коррекцию нельзя включать автоматически при откате,
повторном получении рекомендации или перезапуске. Персональные варианты
требуют отдельной проверки, а не автоматического возврата исходного текста.

### COR-07. Проверка результата и эскалация

Если коррекция не помогла, приложение позволяет связать результат проверки
с исходным обращением. Нельзя бесконечно добавлять похожие или противоречащие
правила. Если безопасная коррекция или проверяемое общее исправление не найдены,
обращение передаётся оператору с историей рекомендаций и их результатов.
Передача дополнительного диагностического контекста сохраняет требования
обезличивания, предпросмотра и согласия из
[diagnostic-reporting.md](diagnostic-reporting.md).

### Критерии приёмки

1. Повторный ответ поддержки не создаёт дубль и не отменяет ручное отключение.
2. Применённая коррекция добавляется только к целевому типу запроса и в пределах
   заданных условий; постоянные инструкции остаются неизменными.
3. После установки релиза с применимым исправлением первый новый запрос уже
   не содержит временную коррекцию; запись и причина отключения видны в истории.
4. Релиз без исправления, только обновление мобильного клиента или исправление
   для другой модели/шаблона не приводят к ложному статусу «Исправлено».
5. Сверка работает без сети; повторный запуск не создаёт повторных переходов
   или уведомлений. Неудавшаяся установка не меняет действующую коррекцию.
6. После отката возобновляется только применимая коррекция, отключённая
   исправлением; вручную отключённая остаётся выключенной.
7. Отредактированная коррекция и вручную вставленный в настройки текст
   не удаляются автоматически; персональные инструкции сохраняются.
8. Неизвестные типы, неприменимые рекомендации и конфликтующие правила
   не попадают в запрос незаметно для пользователя.
