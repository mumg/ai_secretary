# Отчёт об ошибке анализа: требования к первому выпуску

Статус: требования и реализация в исходниках. Обращения доступны в веб-интерфейсе;
из Android и iOS сценарий обращений удалён. Публикация и фактическое обновление
приложений этим изменением не выполнены.

## Назначение и границы

Пользователь сообщает о неверно выделенной задаче или поручении либо об их
отсутствии в письме, переписке или результате встречи. Персональный сервер
собирает минимальный контекст, обезличивает его локально, показывает пользователю
**содержимое отчёта по отдельным редактируемым полям** и отправляет только после
отдельного нажатия «Отправить». JSON остаётся внутренним форматом сервера и
gateway, не передаётся в клиентский UI как текст или редактор. Обычные данные приложения, синхронизация источников и жизненный цикл
задач/поручений не зависят от доступности сервиса отчётов.

В исходниках gateway добавлен
`POST https://connect.ai-secretary.co/api/v1/diagnostic-reports`. До публикации
gateway этот маршрут на действующем сервере недоступен. Исключение для
добровольно подтверждённых обезличенных отчётов внесено в исходники policy;
опубликованные страницы нужно обновить отдельно.

## Сценарии и интерфейс

1. В **веб-интерфейсе** в карточке/деталях задачи, поручения,
   сообщения переписки и результата встречи есть действие «Сообщить об ошибке».
   В веб-клиенте доступны выбор объекта, формирование,
   редактирование, предпросмотр и отправка отчёта через один серверный API.
   Для отсутствующей задачи/поручения пользователь выбирает исходное письмо,
   сообщение или результат встречи. Выбранный объект передаётся как `origin`,
   без копирования его текста клиентом в запрос: контекст собирает сервер.
2. Пользователь выбирает тип: `false_task`, `false_delegation`, `missing_task`,
   `missing_delegation`, `wrong_assignee`, `wrong_content`, `other`. Для пропуска
   он указывает ожидаемое действие и, по возможности, выделяет подтверждающий
   фрагмент источника. Для ложного назначения выбранный элемент уже известен.
   Свободный комментарий и правильный исполнитель необязательны, кроме `other`.
3. Персональный сервер формирует черновик. Экран показывает обезличенные источник,
   соседние сообщения/реплики, результат модели, описание ошибки и метаданные.
   Пользователь может удалить лишний контекст, отредактировать результаты
   обезличивания по отдельным полям. Он может отметить пропущенное имя или название
   системы, изменить метку, заменить фрагмент вручную и применить замену ко всем
   его вхождениям в отчёте. После каждой правки сервер повторно проверяет весь
   внутренний JSON и показывает обновлённые поля; изменение описания ошибки тоже
   проходит обезличивание.
4. Перед отправкой UI сообщает адрес получателя. Кнопка «Отправить»
   активна только после просмотра предпросмотра и явного согласия на передачу
   показанного содержимого. Закрытие экрана или отмена ничего не отправляют.
5. После отправки UI показывает постоянный `report_id` и состояние `queued`,
   `received`, `in_review`, `resolved` или `rejected`. При сетевом сбое отчёт
   остаётся в `queued` с сообщением об ошибке; доступен повтор **того же одобренного JSON**. Новая сборка
   контекста требует нового предпросмотра и согласия. Отчёт не меняет задачу,
   поручение, письмо или результат встречи автоматически.

### Сценарий в веб-интерфейсе

- Действие на задаче и поручении открывает форму с уже выбранным объектом;
  действие на письме/сообщении или результате встречи позволяет сообщить как о
  неверном выделении, так и об отсутствующей задаче или поручении. Из списка
  переписки можно сначала выбрать конкретное сообщение. В веб-интерфейсе
  показываются тип ошибки, выбранный источник, ожидаемый результат и комментарий.
- После выбора типа клиент запрашивает черновик у сервера и показывает состояние
  формирования, включая работу внутренней LLM. Ошибка формирования остаётся на
  экране с возможностью повторить попытку; исходный текст не уходит в gateway.
- Редактор показывает обезличенный контекст, обнаруженные сущности и состав
  отчёта по полям: описание ошибки, ожидаемый результат, найденные задачи и
  поручения, автор, тема и текст каждого сообщения. Каждое текстовое поле имеет
  отдельный редактор; сырой JSON в UI отсутствует. Пользователь может исправить текст, отметить пропущенную
  сущность, заменить её во всех вхождениях и удалить лишний фрагмент. После
  правки клиент получает обновлённые поля и хэш внутреннего JSON с сервера. На небольшом экране
  эти действия остаются доступными без горизонтальной прокрутки формы.
- Финальный экран одинаково сообщает получателя, размер отчёта, предупреждения
  о непроверенных фрагментах и просит отдельного подтверждения. Отправка
  доступна только для просмотренной версии полей; закрытие экрана удаляет или
  даёт истечь локальному черновику без отправки. После отправки показываются
  номер обращения и статус. Список обращений и обновление статуса по номеру
  доступны в веб-интерфейсе; для `queued` доступен повтор отправки.
  Сырой JSON не отображается и не экспортируется из клиентских приложений.

## Сбор контекста на персональном сервере

- Проверить доступ текущего пользователя к выбранному объекту и связанному
  источнику. Для задачи/поручения взять породившее событие через
  `source_event_id`; при отсутствии связи попросить пользователя выбрать источник.
  Для результата встречи взять `source_event_id` и релевантный фрагмент
  расшифровки. Для пропуска начинать с выбранного события.
- Сохранить в отчёте сам источник и ограниченный контекст той же цепочки:
  максимум 8 соседних событий, суммарно не более 64 KiB текста. Для встречи —
  фрагмент вокруг отмеченной реплики, а не всю расшифровку. При усечении явно
  показывать это в предпросмотре. Вложения не отправлять; можно включить уже
  извлечённый текстовый фрагмент, если он служит доказательством и виден в UI.
- Включить наблюдаемое предложение модели и его цитату/уверенность, если они
  сохранены, а также версию приложения, идентификатор модели, хэши промпта и
  схемы. Не включать URL модели, API-ключ, настройки почты, токены, полный
  системный лог, скрытые записи цепочки и внутренние идентификаторы БД.
- Контекст фиксируется при создании черновика. Изменения в источнике после
  предпросмотра не могут незаметно изменить отправляемый JSON.

## Обезличивание и проверка

- Обезличивание выполняется на персональном сервере **до любого обращения к
  gateway**. Имена, email, телефоны, домены, URL, IP-адреса, почтовые адреса,
  номера документов/счетов, имена файлов, подписи, найденные секреты и названия
  информационных систем (включая внутренние приложения, сервисы, платформы и
  кодовые названия) заменяются стабильными внутри отчёта метками (`[USER]`,
  `[PERSON_1]`, `[ORG_1]`, `[SYSTEM_1]`, `[EMAIL_1]`, `[URL_1]`). Роли «автор»,
  «руководитель», «исполнитель» и общий тип системы сохраняются.
  Одинаковая сущность во всём отчёте получает одинаковую метку.
- Абсолютные даты, не важные для ошибки, переводятся в относительные смещения
  от выбранного события; сроки и порядок событий сохраняются. Внешние ID
  источников, сообщений, задач, устройств и установки не попадают в JSON.
  Таблица соответствия меток оригиналам остаётся только в краткоживущем
  локальном черновике и никогда не передаётся.
- Проверка сочетает распознавание структурированных полей и поиск в свободном
  тексте. Словарь названий систем из настроек источников и текста отчёта
  дополняет автоматическое распознавание; он используется только локально и не
  передаётся gateway. Внутренняя LLM приложения, которой уже доверена обработка
  этих источников, дополнительно находит контекстные сущности, которые правила
  могут пропустить: имена людей и организаций, информационных систем, кодовые
  названия и косвенные идентификаторы. Модель возвращает тип и точные фрагменты
  исходного текста, а замены стабильными метками выполняет сервер; LLM не
  переписывает содержимое отчёта и не решает, можно ли его отправлять.
  Обращение за обезличиванием выполняется через тот же доверенный контур LLM,
  который настроен для обычного анализа, без отдельного получателя данных,
  дополнительных внешних логов и передачи исходного текста в gateway. Если
  LLM недоступна или ответ невалиден, черновик строится по правилам, а UI явно
  сообщает о неполной проверке перед ручным просмотром.
  Неизвестные последовательности, похожие на секреты и
  персональные идентификаторы, блокируют отправку до удаления или исправления.
  UI подчёркивает замены и отдельно показывает непроверенные фрагменты:
  автоматическая обработка может пропустить косвенные идентификаторы, поэтому
  финальный просмотр пользователем обязателен. Ручная правка не может вернуть
  исходное значение в отправляемый JSON незаметно: после неё снова выполняются
  поиск чувствительных данных и проверка всех вхождений изменённой метки.
- Предпросмотр и отправка используют одну каноническую сериализацию. Сервер
  принимает `draft_id` и хэш показанного JSON, а не заново собирает данные при
  отправке. В логах и аналитике — только `report_id`, размеры, код ошибки и
  состояние доставки; тело и таблица замен не логируются.

## Формат JSON v1

Пример: [diagnostic-report.example.json](diagnostic-report.example.json). Поля:

- `schema_version`, случайный `report_id`, `issue.type`, `issue.user_comment`,
  `issue.expected` и `issue.observed`;
- `origin.kind` (`task`, `delegation`, `conversation_event`, `meeting_result`) и
  локальная **метка** объекта в контексте, без исходного UUID;
- `context.events` — обезличенные текстовые события с ролями и относительным
  временем, `context.truncated` — признак усечения;
- `analysis` — предложения модели и доказательства по этому источнику;
- `diagnostics` — версия приложения/модели и хэши контрактов без секретов;
- `redaction` — версия алгоритма и счётчики замен без таблицы соответствия.

Сервер отклоняет неизвестную версию, неожиданные поля и payload более 256 KiB.
Текстовые поля и массивы имеют отдельные лимиты. Не прикладываются файлы,
изображения, аудио или полная расшифровка.

## API

### Персональный сервер для веб-клиента

- `POST /api/v1/diagnostic-reports/drafts` — принять тип ошибки и локальный ID
  выбранного объекта, проверить права, собрать/обезличить и вернуть `draft_id`,
  список редактируемых полей, предупреждения и `payload_sha256`. Внутренний JSON
  остаётся на персональном сервере и не передаётся клиенту.
- `PATCH /api/v1/diagnostic-reports/drafts/{draft_id}` — принять изменения
  отдельных полей и правил замены; сервер повторяет обезличивание и возвращает
  обновлённые поля, предупреждения и новый хэш.
- `POST /api/v1/diagnostic-reports/drafts/{draft_id}/send` с
  `payload_sha256` — отправить ровно одобренную версию. В ответе локальный статус
  и квитанция gateway. Черновик истекает через 24 часа и удаляется при отмене.
- `GET /api/v1/diagnostic-reports` и
  `GET /api/v1/diagnostic-reports/{report_id}` — список и актуальное состояние
  без текста отчёта. `POST /api/v1/diagnostic-reports/{report_id}/retry`
  повторяет отправку с тем же хэшем и `report_id`.

### Gateway

- `POST /api/v1/diagnostic-reports` — HTTPS/mTLS с сертификатом роли `server`.
  Идентичность установки берётся из сертификата, не из JSON. Заголовок
  `Idempotency-Key: <report_id>`; повтор с тем же телом возвращает ту же
  квитанцию, с другим — `409`. Успех: `202` и `{report_id, accepted_at, state}`.
  Ошибки: `400` схема, `401/403` идентичность, `413` размер, `429` лимит,
  `503` хранилище. Для маршрута нужен отдельный лимит тела и rate limit,
  поскольку действующий общий декодер gateway ограничен 32 KiB.
- В административном API gateway через локальный Unix socket:
  `GET /api/v1/admin/diagnostic-reports` (пагинация и фильтры),
  `GET /api/v1/admin/diagnostic-reports/{report_id}` (выгрузка JSON),
  `DELETE /api/v1/admin/diagnostic-reports/{report_id}`. Публичной выдачи
  содержимого отчётов нет. Доступ к выгрузке журналируется.
- Хранение шифруется, доступ ограничен обработчиками отчётов; исходные письма,
  таблицы замен и секреты не сохраняются. Предлагаемый срок хранения — 90 дней
  с автоматическим удалением; это значение нужно согласовать с policy и
  процедурой разбора. Ошибка gateway не приводит к передаче отчёта иным путём.

## Критерии приёмки

1. Все четыре стартовые точки (задача, поручение, переписка, результат встречи)
   открывают черновик; пропущенную задачу/поручение можно указать без существующего
   объекта. Архивный/завершённый статус не мешает сообщить об ошибке.
2. До подтверждения отсутствует исходящий запрос с содержимым отчёта. Тело
   отправки байт-в-байт соответствует внутреннему JSON, который сформирован из
   показанных полей, и его хэшу; сырой JSON не показывается в интерфейсе.
3. Тестовые письма с повторяющимися именами, адресами, URL, телефонами, сроками,
   подписями, названиями информационных систем и токенами получают устойчивые
   метки; оригиналы не встречаются в JSON, HTTP-запросе, gateway-хранилище и
   логах. Пользователь может исправить пропущенное название системы и увидеть
   его замену во всех фрагментах до отправки. Проверяются случаи, где название
   системы или человека можно распознать только из контекста: LLM предлагает
   фрагмент, сервер заменяет все его вхождения. При ошибке LLM действуют правила
   и ручная правка; UI показывает, что контекстная проверка не выполнена.
4. Неверное и пропущенное назначение различаются в JSON; доказательство и
   корректный ожидаемый результат видны пользователю до отправки.
5. Повтор отправки не создаёт дубль; сбой сети не меняет локальные задачи и
   поручения. Несовпадение хэша и попытка отправить чужой черновик отклоняются.
6. Gateway принимает отчёт только от действующего сертификата роли `server`;
   административная выгрузка недоступна в публичном HTTP API.
7. Набор сценариев выполняется в веб-интерфейсе: ошибочная
   задача, ошибочное поручение, пропущенная задача/поручение в сообщении и в
   результате встречи, редактирование обезличивания, повтор формирования,
   предпросмотр, отмена и отправка. `origin` указывает на
   один и тот же объект, а JSON и хэш формирует только персональный сервер.

## Решения перед реализацией

- Нужна ли отправка из установки без регистрации в gateway? Для первого выпуска
  отчёт остаётся в локальной очереди `queued` до появления mTLS-связи с gateway.
- Нужен ли пользователю контакт для обратной связи? По умолчанию отчёт без
  контактных данных; отдельное добровольное поле потребует отдельного согласия.
- Подтвердить срок хранения 90 дней и перечень лиц, имеющих доступ к выгрузке.
