# Требования к системе анализа переписки и контроля задач

Статус: требования зафиксированы, разработка MVP начата  
Последнее обновление: 2026-09-12  
Версия контекста: 1.15

Проект требований к пользовательскому WEB-интерфейсу на основе Android:
[WEB_UI_REQUIREMENTS.md](WEB_UI_REQUIREMENTS.md). Новые предложения в нём требуют
обсуждения и не считаются подтверждёнными требованиями этого документа.

## 1. Назначение системы

Локальная персональная система должна подключаться к нескольким источникам переписки, анализировать письма, сообщения и расшифровки встреч локальной моделью Qwen через Ollama, выделять поручения для пользователя и превращать их в контролируемые задачи.

Пользователь работает с задачами через Android-приложение. Система уведомляет о новых и приближающихся задачах, отслеживает возможное выполнение по исходящим ответам и позволяет вручную управлять задачами.

Содержимое почты, чатов, расшифровок встреч и LLM-анализ остаются на персональном локальном сервере. Firebase используется только как транспорт технических push-сигналов и не должен получать тексты переписки или задач.

## 2. Подтверждённые продуктовые требования

### 2.1 Пользователь и устройства

- В системе один пользователь.
- Поддерживается до 2–3 Android-устройств одного пользователя.
- Роли, многопользовательская регистрация и разделение организаций не требуются.
- Каждое Android-устройство должно иметь отдельную идентичность и отдельный клиентский сертификат.

### 2.2 Источники переписки

- Поддерживаются несколько источников одновременно; количество источников заранее не ограничивается.
- Типы источников:
  - электронная почта по IMAP;
  - локальный Microsoft Exchange;
  - мессенджеры и коммуникационные платформы, в том числе МТС Линк;
  - расшифровки встреч;
  - личные чаты пользователя.
- Источники подключаются, изменяются, отключаются и удаляются через веб-панель сервера.
- Удаление источника также удаляет импортированные из него события, нитки, вложения,
  задачи, напоминания и производные элементы плана; ручные задачи сохраняются.
- В веб-панели ведётся редактируемый справочник тегов: теги можно добавлять,
  переименовывать и удалять.
- Источнику можно назначить несколько тегов только из справочника; один тег может быть
  назначен нескольким источникам. Удаление тега снимает его со всех источников.
- В дальнейшем теги источников используются как фильтры воронки поиска.
- Веб-панель позволяет проверить соединение с адаптером до начала штатной синхронизации.
- Для почты необходимо анализировать входящие и отправленные письма.
- Для коммуникационных платформ необходимо получать личные сообщения, доступные пользователю расшифровки встреч, участников, авторов реплик и временные метки.
- При первом подключении загружается доступная история за последние 30 дней, если источник позволяет это сделать.
- Полный текст писем, сообщений и расшифровок разрешено хранить локально.
- Для Exchange предпочтителен EWS, если он доступен; IMAP является допустимой альтернативой.
- Точная версия Exchange, доступность EWS/IMAP и способ аутентификации пока не определены.
- Источник МТС Линк использует наблюдаемый API шлюза `gw.mts-link.ru`: раз в 15 минут получает
  список доступных встреч, пакетно проверяет состояние расшифровок и загружает каждую новую
  готовую расшифровку ровно один раз. Access token вводится и обновляется через веб-панель и
  хранится в зашифрованном виде; протокол обновления токена пока не известен.
- Для собственного анализа Qwen используются только структурированные исходные реплики с
  авторами и временными метками. Готовое AI-резюме и готовые задачи МТС Линк не запрашиваются и
  не подмешиваются в исходный текст, даже если присутствуют в начале текстовой выгрузки.
- Каждый тип источника реализуется отдельным адаптером и преобразует данные в единый внутренний формат.
- Произвольный внешний парсер может зарегистрировать пассивный источник задач через mTLS API и
  пакетно передавать уже сформированные задачи. Пара `source_id + external_id` обеспечивает
  идемпотентность; повторная загрузка возвращает текущий статус и признак активности без создания
  дубля. Полный снимок может явно закрыть отсутствующие задачи, частичная загрузка их не изменяет.
- Единый формат события переписки должен включать источник, внешний идентификатор, тип события, цепочку/чат/встречу, автора, участников, время, текст, вложения и ссылку на оригинал, если она доступна.

### 2.3 Выделение задач из переписки

- Письма, сообщения личных чатов и расшифровки встреч анализируются локальной LLM.
- Пока очередь анализа не пуста, worker берёт следующий пакет сразу, без ожидания интервала
  опроса; настроенный интервал применяется только к пустой очереди.
- Недоступность Ollama, ошибка HTTP или некорректный структурированный ответ модели не должны
  приводить к потере события. Первичный анализ и фоновое построение смыслового индекса используют
  сохраняемую в PostgreSQL очередь повторов с экспоненциальной задержкой от 30 секунд до одного
  часа. После восстановления Ollama обработка продолжается автоматически; число попыток и
  последняя ошибка сохраняются для диагностики.
- В веб-панели настраиваются списки стоп-слов/фраз и исключённых e-mail адресов.
  При совпадении темы или текста без учёта регистра либо точном совпадении адреса отправителя
  или участника событие сохраняется и остаётся доступным поиску, но не передаётся LLM и не
  создаёт автоматическую задачу. Поля адресов разбираются независимо друг от друга, чтобы
  некорректное отображаемое имя одного участника не мешало применить исключение к другому.
- После изменения стоп-слов или исключённых адресов сервер сразу повторно проверяет весь
  сохранённый архив. Новые совпадения исключаются из автоматического анализа, а записи,
  переставшие совпадать с пользовательскими фильтрами, возвращаются в очередь `PENDING`.
- Технические ответы о принятии, отклонении или предварительном принятии встречи, а также
  автоматические ответы об отсутствии распознаются по MIME-заголовкам и устойчивым префиксам
  темы. Они сохраняются как технические события, но исключаются из LLM-анализа, поиска и
  формирования/обновления ниток переписки.
- Для каждого email Qwen определяет, является ли сообщение массовой рассылкой без ожидания
  личного ответа: новостной или рекламной рассылкой, автоматическим дайджестом либо общим
  массовым объявлением. Обычная рабочая переписка с несколькими адресатами рассылкой не
  считается. Решение применяется автоматически при уверенности не ниже 0,85.
- Рассылочное сообщение сохраняется в полном архиве и остаётся доступным для поиска и анализа,
  но не создаёт задачи, не включается в резюме нитки и не показывается во вкладке «Переписки».
  Уже сохранённая почта классифицируется Qwen пакетами в фоне; версия и уверенность решения
  сохраняются в PostgreSQL, а затронутая нитка перестраивается после каждого исключения.
- В описании пользователя через веб-панель задаются только варианты имени и фамилии. Почтовые
  адреса пользователя автоматически выводятся из настроек подключённых источников (`username`
  для IMAP и основной SMTP-адрес для Exchange) и отдельно не вводятся.
- Событие может содержать задачу для пользователя только при выполнении хотя бы одного условия:
  пользователь прямо упомянут через `@`; пользователь является единственным получателем; либо
  пользователь находится среди нескольких получателей и в тексте есть обращение к нему по имени
  или фамилии. Ограничение вычисляется сервером до LLM и повторно применяется после её ответа.
- При выполнении правила назначения задача создаётся автоматически, если наличие поручения и
  исполнитель определены с достаточной уверенностью.
- Совпадение имени с пользователем допустимо, если среди известных участников переписки нет
  тёзок. Чужой почтовый адрес не может считаться адресом пользователя из-за совпадения имени.
  При наличии тёзок Qwen определяет исполнителя каждого поручения по адресам, полным именам,
  авторам реплик и предыдущим договорённостям. Для автоматического назначения требуется
  подтверждающая цитата из оригинала, идентифицирующая пользователя; совпадения имени,
  высокой уверенности модели или одного резюме недостаточно. Неразрешённая неоднозначность
  приводит к `NEEDS_CONFIRMATION`; явное назначение другому человеку не создаёт задачу пользователя.
- Для встречи исполнитель определяется по прямому поручению, имени пользователя, контексту реплик и списку участников.
- Для личного чата учитываются направление сообщения, автор, участники и контекст предыдущих сообщений.
- Если наличие поручения или исполнитель определены недостаточно уверенно, создаётся кандидат со статусом `NEEDS_CONFIRMATION`.
- Кандидат должен быть подтверждён или отклонён через Android-приложение.
- У задачи должна сохраняться связь с исходным письмом, сообщением, чатом или встречей, на основании которых она создана.
- Желательно сохранять доказательный фрагмент текста, по которому выделена задача.
- Необходимо выявлять повторно полученные события и дубликаты задач.
- Одна и та же переписка или расшифровка может поступить через несколько настроенных источников или повторный экспорт.

### 2.4 Ручное управление задачами

Android-приложение должно позволять:

- создавать задачу вручную;
- запускать голосовое добавление долгим нажатием на кнопку `+`; обычное нажатие открывает
  ручную форму без микрофона в поле названия;
- распознавать голосовую запись системными средствами Android с предпочтением офлайн-режима,
  затем передавать текст локальной Qwen для формализации названия, описания, приоритета,
  due date и времени выполнения; исходный распознанный текст сохраняется вместе с задачей;
- задавать или менять приоритет;
- задавать или менять due date;
- отмечать задачу выполненной;
- редактировать задачу;
- при нажатии на задачу просматривать её источник, метаданные и полный оригинальный текст
  письма, сообщения или расшифровки; экран показывает источник, отдельно дату и время,
  тему при её наличии и краткую выжимку из задачи; для ручной задачи явно показывается
  отсутствие источника; детали открываются отдельным Android Activity, а не всплывающим окном;
- вручную устанавливать напоминание для отдельной задачи.
- использовать единую тёмную цветовую схему; карточка задачи окрашивается в тёмный оттенок
  по приоритету, а приоритет выводится на ней один раз понятной русской меткой;
- располагать будильник и чекбокс в строке срока и просрочки; если у задачи установлено
  активное напоминание, выделять обводку будильника отдельным цветом.
- иметь отдельную вкладку «Переписки» со списком резюме ниток, отсортированным по времени
  последнего сообщения; следующие страницы подгружаются автоматически при пролистывании.

### 2.5 Нитки переписки

- Сообщения связываются в нитку внутри источника по `Thread-Index`, `References`,
  `In-Reply-To`, Exchange Conversation ID или идентификатору чата/встречи.
- Для сообщения без идентификатора цепочки создаётся самостоятельная нитка по внешнему ID.
- Сервер хранит название, участников, число сообщений, диапазон дат и актуальное резюме нитки.
- Нажатие на плитку переписки открывает отдельный Android Activity с источником, периодом,
  участниками, общим резюме Qwen и списком сообщений от новых к старым. Каждая карточка сообщения
  показывает направление, время, автора и краткую выжимку; нажатие открывает полный оригинал.
- После получения и анализа нового сообщения Qwen обновляет резюме, используя предыдущее
  резюме и последние сообщения вместо повторной передачи всей истории.
- Для существующего архива нитки создаются миграцией; отсутствующие смысловые резюме
  постепенно достраиваются фоновым worker.
- Календарные приглашения не включаются во вкладку и резюме «Переписки». Для встреч существует
  отдельная вкладка с предстоящими событиями, временем, местом и организатором. Нажатие на
  встречу здесь и в «Плане на сегодня» открывает подготовленный контекст; исходное приглашение
  доступно отдельной кнопкой на этом экране.
- При формировании плана автоматически готовится контекст только встреч сегодняшнего дня
  в часовом поясе сервера. Контекст сохраняется в БД
  и содержит резюме предыдущих встреч, решения, договорённости и открытые вопросы из связанных
  переписок. Каждое использованное письмо или итог встречи доступно по ссылке на источник.
- Для поиска связи используются тема, календарная связь, ссылка МТС Линк и цепочка приглашения;
  Qwen проверяет смысловую релевантность с учётом повестки, участников и дат. Общее название
  «Встреча» или совпадение одного участника само по себе недостаточно. Ответственные и сроки
  указываются только по источникам; тёзки различаются по контексту и адресам.
- Для будущих встреч контекст создаётся только по кнопке «Создать контекст» в деталях.
  Открытие деталей само по себе не запускает Qwen. Готовый контекст сразу отображается;
  кнопка «Обновить контекст» позволяет повторно собрать его с новыми материалами.
- Запросы по кнопке обрабатываются первыми; автоматическая очередь ограничена сегодняшним планом.
  Источники сегодняшних встреч перепроверяются раз в 15 минут без повторного Qwen при неизменных
  материалах. У будущих встреч автоматического обновления контекста нет.
- Завершение подготовки или обновления, явно запрошенного кнопкой, сопровождается push с
  переходом к нужной встрече. Автоматическая подготовка и обновление сегодняшнего плана
  уведомлений не создают.
  В FCM передаются только тип события и идентификатор; при временном сбое отправка повторяется.
  Повторная проверка неизменного кеша не создаёт уведомление.
- Markdown в контексте и итогах встреч отображается с выделениями, заголовками и списками;
  служебные маркеры `**` не выводятся вместо полужирного текста.
- Изменение встречи аннулирует устаревший контекст; результат начатой до изменения генерации
  не должен его перезаписывать. Экран показывает подготовку, отсутствие источников, ошибку,
  отмену или завершение встречи, а загрузка контекста через API не ожидает ответа Qwen.
- Массовые рассылки, распознанные Qwen с достаточной уверенностью, также не участвуют в числе
  сообщений, участниках и актуальном резюме нитки.
- Встречи текущего дня включаются в «План на сегодня» отдельным блоком и не преобразуются для
  этого в задачи. Обновления и отмены связываются с исходной встречей по календарному UID.
- Время встреч показывается в часовом поясе сервера. Для текущего локального Exchange его
  календарные значения с ошибочным UTC-маркером интерпретируются как локальное время без
  дополнительного сдвига на три часа; уже локализованные значения не изменяются.
- Завершившиеся и отменённые встречи автоматически скрываются из вкладки «Встречи» и блока
  сегодняшнего плана. Android проверяет время окончания локально каждую минуту, поэтому для
  скрытия карточки не требуется ручное обновление.
- HTTP(S)-ссылки в поле места встречи отображаются как активные ссылки и открываются системным
  обработчиком ссылок. Нажатие на остальную область карточки открывает детали и контекст встречи.
- Расшифровки МТС Линк отображаются в отдельной вкладке «Итоги» и не создают нитки во вкладке
  «Переписки». Карточка результата содержит время, состояние анализа Qwen, новое резюме,
  решения и связь с календарным событием; нажатие открывает полный оригинал расшифровки.
- Результат МТС Линк связывается с событием Outlook по совпадающему ID МТС Линк из ссылки,
  если пересечение с окном Outlook составляет не менее 80% длительности встречи МТС Линк.
  Для каждого временного кандидата Qwen сравнивает тему/описание календаря с резюме, ключевыми
  словами, решениями и договорённостями фактического обсуждения. Связь устанавливается только
  при единственном смысловом совпадении с уверенностью не ниже 0,75. Один ID может использоваться
  в разных календарных встречах; одинаковый ID сам по себе не объединяет их результаты.
  При нескольких смысловых совпадениях связь считается неоднозначной и не устанавливается.
  Общие части пути, идентификаторы владельца и пользователя не являются ID встречи.
  Семантическое решение сохраняется в технических метаданных и применяется одинаково при любом
  порядке поступления приглашения и расшифровки.
- Обычные письма дополнительно классифицируются как возможные итоги уже состоявшейся встречи.
  Приглашения, повестки, напоминания, ответы о принятии/отклонении и автоответы итогами не
  считаются. Положительный результат с достаточной уверенностью сохраняется в «Итогах».
- Почтовый итог присоединяется к результату МТС Линк при общей подтверждённой календарной
  встрече и совпадающем ID МТС Линк. Время отправки письма не является временем начала встречи.
  Для писем календарное событие определяется по названию, ссылке и, при наличии, цепочке
  приглашения; при нескольких завершённых кандидатах за 45 дней письмо остаётся отдельным.
  Похожая тема или общий ID без подтверждённого календарного события не объединяют результаты.
  При позднем поступлении расшифровки подтверждённые почтовые дополнения переносятся к ней.
- В списке отображается одна карточка встречи с короткой выжимкой основных договорённостей из
  всех связанных материалов. Нажатие открывает отдельный экран с датой и временем, темой,
  участниками, автоматическим резюме расшифровки, общими решениями и договорённостями, а также
  отдельными резюме писем участников со ссылкой на каждый оригинал.

### 2.6 Отслеживание выполнения

- Сервер синхронизирует папки исходящих писем.
- Ответное письмо связывается с исходной перепиской по `Message-ID`, `In-Reply-To`, `References`, идентификаторам Exchange и резервным признакам.
- Для мессенджеров и встреч выполнение может определяться по последующим сообщениям, ответам в том же чате или более поздним фрагментам расшифровки.
- Наличие содержательного ответа не закрывает задачу автоматически.
- Если ответ похож на передачу результата, задача переводится в состояние `POSSIBLY_COMPLETED`.
- После перехода в `POSSIBLY_COMPLETED` на телефон отправляется уведомление.
- Пользователь подтверждает выполнение вручную.

Предполагаемые состояния задачи:

- `NEEDS_CONFIRMATION` — требуется подтвердить, что событие переписки содержит задачу для пользователя;
- `NEW` — новая задача;
- `IN_PROGRESS` — задача выполняется;
- `POSSIBLY_COMPLETED` — обнаружен ответ или другой признак выполнения;
- `COMPLETED` — выполнение подтверждено;
- `CANCELLED` — задача отменена.

### 2.7 Приоритет и ранжирование

- Задачи ранжируются по важности и сроку выполнения.
- Пользователь должен иметь возможность просматривать все активные задачи без ограничения количества.
- Должен поддерживаться просмотр задач, отсортированных по due date для разных приоритетов.
- Новая критическая задача автоматически добавляется в актуальный план и вызывает уведомление.
- Незавершённые задачи на следующий рабочий день ранжируются заново вместе с остальными, а не переносятся с прежним порядком.
- Ручной приоритет должен иметь преимущество перед предположением LLM.
- Итоговый рейтинг должен быть объяснимым пользователю.

### 2.8 Рабочее время и производственный календарь

- Часовой пояс задаётся в настройках.
- Рабочее время: с 10:00 до 17:00.
- Используется производственный календарь России, включая праздники и переносы рабочих дней.
- Серверу разрешено автоматически обновлять производственный календарь через интернет.
- Локально хранится кэш календаря, чтобы расчёт сроков не зависел от постоянного доступа к интернету.
- Если срок попадает на нерабочий день, он переносится на предыдущий рабочий день.
- Относительные формулировки (`завтра`, `к пятнице`, `до конца дня`) интерпретируются с учётом рабочего времени, часового пояса и производственного календаря.

### 2.9 Функция «План на сегодня»

- План формируется сервером ежедневно в 08:00 в настроенном часовом поясе.
- Выбран формат ранжированного списка, без временных слотов и без обязательной оценки продолжительности задач.
- Количество задач в плане не ограничивается.
- Пользователь может видеть все задачи, ранжированные по due date и приоритету.
- Просроченные задачи и задачи с ближайшими сроками должны подниматься в списке.
- Критическая новая задача автоматически добавляется и сопровождается уведомлением.
- После изменения задач план пересчитывается; незавершённые задачи на следующий день проходят повторное ранжирование.
- Пользователь может вручную добавить напоминание к задаче.

### 2.10 Уведомления

- Используется Firebase Cloud Messaging (FCM).
- Сервер отправляет предусмотренные уведомления всегда; показывать, скрывать или отключать их решают настройки уведомлений Android на телефоне.
- В push-сообщение нельзя включать тему или название переписки, название задачи, автора/отправителя, текст или due date.
- FCM передаёт только технический тип события и непрозрачный идентификатор/сигнал синхронизации.
- После получения сигнала приложение забирает содержимое через защищённый API.
- Нужны уведомления как минимум для:
  - новой задачи;
  - задачи, требующей подтверждения;
  - новой критической задачи;
  - состояния `POSSIBLY_COMPLETED`;
  - ручного напоминания;
  - приближения срока;
  - наступления просрочки;
  - повторного напоминания о просроченной задаче.
  - готового ответа Qwen на ранее отправленный вопрос чата; если экран чата открыт,
    ответ показывается в нём без системного уведомления.

### 2.11 Вложения

В первой версии анализируются:

- PDF с текстовым слоем;
- Word (`.docx`);
- Excel (`.xlsx`).

Не входят в обязательный объём первой версии:

- OCR сканированных PDF;
- анализ изображений;
- старые форматы `.doc` и `.xls` — могут быть включены опционально.

Требования безопасности обработки вложений:

- не выполнять макросы;
- не обновлять внешние ссылки и источники данных;
- не переходить по ссылкам из документов;
- использовать ограничения размера, времени и ресурсов;
- обрабатывать потенциально опасные документы изолированно;
- явно показывать ошибку для повреждённых или защищённых паролем документов.

### 2.12 Развёртывание

- Исходники проекта и Android-клиента остаются в локальной рабочей копии на Mac.
- Целевой сервер разработки и эксплуатации задаётся локальной deployment-конфигурацией и не
  фиксируется в репозитории вместе с адресами и SSH-учётными данными.
- После изменения и локальной проверки исходники сразу синхронизируются в `/opt/secretary`,
  после чего необходимые образы пересобираются и сервисы обновляются через Docker Compose.
- Синхронизация исходников не должна перезаписывать persistent volumes, рабочую PostgreSQL,
  каталог серверных секретов, сертификаты или отдельно запущенный контейнер Ollama.
- Все серверные компоненты приложения, кроме отдельно управляемого Ollama, должны запускаться единым Docker Compose-проектом.
- Ollama является внешней локальной зависимостью, уже работает отдельно и не входит в Compose-проект приложения.
- Штатный запуск серверного контура приложения должен выполняться командой `docker compose up -d`; Ollama к этому моменту должна быть доступна по настроенному адресу.
- На хосте не должны требоваться отдельно установленные Python, Java, Node.js, PostgreSQL или другие runtime-зависимости приложения.
- На хосте требуются Docker Engine, Docker Compose, отдельно работающая Ollama с NVIDIA Container Toolkit/драйвером и системные средства для хранения bootstrap-секретов и резервных копий.
- Через Compose должны запускаться как минимум:
  - reverse proxy и mTLS-шлюз;
  - backend API;
  - фоновый обработчик источников переписки, LLM-заданий, планов и уведомлений;
  - PostgreSQL;
  - изолированный обработчик вложений;
  - служебные одноразовые контейнеры для миграций и других операций, если они потребуются.
- Постоянные данные PostgreSQL и приложения должны храниться в явно объявленных persistent volumes. Данные и модели Ollama обслуживаются её отдельным развёртыванием.
- Рабочие настройки хранятся в PostgreSQL и управляются через веб-панель.
- В контейнеры монтируются только bootstrap-секреты PostgreSQL, ключ шифрования приложения и TLS/mTLS-материалы; они не встраиваются в образы.
- Внутренние сервисы приложения объединяются изолированной Docker-сетью; наружу публикуется только порт 443 reverse proxy.
- Backend получает контролируемый сетевой доступ к отдельно работающей Ollama через настраиваемый `base_url`; адрес Ollama не должен быть публично доступен из интернета.
- Для основных контейнеров задаются healthcheck, порядок зависимостей и политика автоматического перезапуска.
- PostgreSQL хранит отдельную целочисленную версию прикладной схемы и ревизию Alembic. После
  успешной миграции запись версии обновляется автоматически.
- API, worker и каждый будущий сервис, использующий прикладные таблицы, до начала работы ожидают,
  пока версия схемы не станет не ниже минимальной версии, зафиксированной в его сборке.
- Migration-service не применяет этот барьер, поскольку именно он переводит схему в требуемое
  состояние. Ожидание совместимости дополняет, но не заменяет Compose `depends_on`.
- Версии контейнерных образов должны быть зафиксированы; использование плавающего тега `latest` для рабочего развёртывания не допускается.
- Ollama, Android-приложение, внешние почтовые серверы, коммуникационные платформы и облачный сервис FCM в Compose-проект приложения не входят.

### 2.13 Языки разработки

- Обязательный язык разработки серверной части — Python 3.
- На Python 3 реализуются backend API, фоновые обработчики, адаптеры источников, LLM-конвейер, ранжирование, календарь и обработка документов.
- Точная minor-версия Python должна быть зафиксирована в Docker-образе перед началом реализации; плавающий базовый тег Python не допускается.
- Установка Python на хост не требуется: приложение запускается только в контейнерах.
- Обязательный язык разработки Android-приложения — Kotlin.
- Точная версия Kotlin, минимальная версия Android и target SDK должны быть зафиксированы перед реализацией.
- Jetpack Compose для интерфейса и Room для локального кэша являются планируемыми библиотеками, но не заменяют обязательное требование использовать Kotlin.

### 2.14 Чат по архиву

- Во вкладках «Задачи», «Встречи» и «Переписки» доступен полнотекстовый поиск с морфологией
  русского языка и точным многоязычным совпадением. Поиск выполняется сервером по всему
  набору данных соответствующей вкладки, сохраняет её основной порядок сортировки и работает
  совместно с постраничной загрузкой встреч и переписок.
- По задачам индексируются название, описание и доказательный фрагмент; по встречам — название,
  место, организатор и участники; по перепискам — тема, актуальное резюме и участники.
- В Android-приложении доступен отдельный чат для взаимодействия с локальной Qwen.
- Чат отвечает на вопросы по сохранённым задачам, письмам, сообщениям, расшифровкам встреч
  и извлечённому тексту вложений.
- Каждое полученное событие переписки сохраняется до LLM-анализа и остаётся доступным для
  поиска, даже если из него не была создана задача.
- Перед запросом к Qwen сервер выбирает релевантные записи, соблюдает настроенный лимит
  контекста и не передаёт модели весь архив без необходимости.
- Поиск гибридный: быстрый внутренний отбор выполняется по заранее подготовленным категориям,
  ключевым словам, людям, организациям, решениям, договорённостям и резюме цепочек; при нехватке
  индекса допускается резервный поиск по оригиналу.
- Предварительные совпадения не показываются пользователю как релевантные. Компактный список
  кандидатов обязательно проверяется Qwen по смыслу вопроса.
- Отправка вопроса не удерживает Android-клиент до завершения Qwen. Сервер сразу сохраняет
  запрос в долговечной очереди PostgreSQL и возвращает его идентификатор; пользователь может
  отправить следом ещё несколько независимых вопросов.
- Worker обрабатывает очередь отдельно от HTTP-запросов, сохраняет статус, ответ и источники.
  При недоступности Ollama запрос не теряется и повторяется с экспоненциальной задержкой.
- Экран чата показывает отдельный статус для каждого вопроса и периодически синхронизируется
  с сервером. Готовый ответ появляется в открытом чате автоматически; если чат закрыт, сервер
  отправляет обезличенный FCM-сигнал, после которого приложение получает текст по mTLS и
  показывает push с кратким ответом.
- Ответ сопровождается ссылками на использованные задачи и события с источником, датой и
  кратким фрагментом оригинала.
- История текущего диалога передаётся в последующих запросах, чтобы поддерживать уточняющие
  вопросы.
- Содержимое архива считается недоверенными данными: инструкции внутри писем, сообщений и
  документов не должны изменять системные правила чата.
- API поиска поддерживает ограничение по тегам источников для последующего интерфейса воронки
  поиска.

### 2.15 Эргономика Android-интерфейса

- Основной сценарий рассчитан на управление большим пальцем правой руки при удержании телефона
  одной рукой.
- Основные глобальные действия располагаются в нижней правой части экрана: добавление задачи,
  чат, обновление, сортировка и настройки.
- На карточке задачи чекбокс завершения находится справа, а добавление напоминания представлено
  расположенной рядом пиктограммой будильника.
- Интерактивные области основных действий должны иметь размер не менее 48 dp; для частых действий
  используются области 52–64 dp.

## 3. Сетевая безопасность

- При разработке и диагностике нельзя читать из рабочей базы темы, тела, отправителей,
  адресатов или иные данные писем для поиска примеров. Содержательные примеры предоставляет
  пользователь по явному запросу; без них допускаются только технические метрики, агрегированные
  состояния и искусственные тестовые сообщения.
- Если для диагностики необходим смысловой анализ писем из рабочей базы, его разрешено выполнять
  только внутри локального контура моделью Qwen через настроенный приватный URL Ollama. Текст,
  тема, отправители, адресаты и другие детали писем не должны выводиться в команды, журналы,
  ответы инструментов или контекст ассистента; наружу передаются только обезличенные выводы,
  агрегаты и технические статусы.
- API сервера доступно через публичный адрес.
- Входящие API-соединения разрешены только по HTTPS с обязательным mTLS.
- Наружу публикуется только TCP-порт 443.
- PostgreSQL, Ollama и внутренние сервисы не публикуются в интернет.
- Для сервера используется обычный TLS-сертификат с корректным публичным DNS-именем.
- Для клиентских сертификатов используется отдельный локальный центр сертификации.
- Каждый телефон получает отдельный сертификат, который можно отозвать независимо.
- Предпочтительная схема подключения устройства: приватный ключ генерируется внутри Android Keystore, приложение создаёт CSR, а сервер подписывает его после одноразового подтверждения/QR-кода.
- Пароли и токены внешних источников и Firebase service account вводятся через веб-панель и хранятся в PostgreSQL с аутентифицированным шифрованием.
- Ключ шифрования приложения хранится вне PostgreSQL как Docker-mounted secret и включается в защищённую резервную копию.
- TLS-ключи и CA не вводятся через веб-панель: они остаются bootstrap-материалами reverse proxy.

## 4. Локальная LLM и оборудование

### 4.1 Ollama

- Ollama развёрнута и управляется отдельно от Docker Compose-проекта приложения.
- Адрес экземпляра задаётся в локальных настройках и не публикуется в репозитории.
- Docker-образ: `ollama/ollama:0.32.13`.
- Установленная модель для основной обработки: `qwen3.8:27b-q4_K_M`.
- Дополнительные локальные записи:
  - `qwen3.8:latest`;
  - `qwen3.8:27b`.
- Архитектура модели: `qwen35`.
- Параметры: 27.3B.
- Квантование: `Q4_K_M`.
- Максимальный заявленный контекст: 262144 токена.
- Модель требует Ollama не ниже 0.32.12; установленная версия подходит.
- Возможности: completion, vision, tools, thinking.
- Лицензия модели: Apache 2.0.

Предварительные настройки инференса:

- использовать конкретное имя модели, не `latest`;
- один LLM-запрос одновременно;
- все слои модели принудительно размещать на GPU (`num_gpu=-1`), без CPU-инференса;
- после первого прогрева не выгружать модель из VRAM (`keep_alive=-1` / `OLLAMA_KEEP_ALIVE=-1`);
- стартовый рабочий контекст 16384 токена;
- конфигурируемый прикладной лимит контекста — до 131072 токенов;
- не использовать заявленный моделью максимум 262144 без специальных тестов;
- температура около 0.1 для воспроизводимого извлечения;
- требовать структурированный JSON по схеме;
- thinking по умолчанию отключить ради скорости;
- перед отправкой в модель удалять подписи и повторные цитаты;
- длинные цепочки и чаты сворачивать: последнее событие полностью плюс резюме истории.

### 4.2 Серверное оборудование

- GPU: NVIDIA GeForce RTX 3090, 24 ГБ VRAM.
- Драйвер NVIDIA: 580.173.02.
- CUDA, показываемая драйвером: 13.0.
- CPU: Intel Xeon E5-2670 0 @ 2.60 GHz.
- CPU: 8 физических ядер / 16 потоков.
- RAM: 61 GiB, на момент проверки доступно около 60 GiB.
- Swap: 8 GiB.

Ограничения:

- основная LLM-нагрузка должна исполняться на GPU;
- CPU-инференс нежелателен из-за старого процессора без AVX2;
- следует избегать вытеснения части модели/контекста в RAM;
- разбор переписки и документов может выполняться несколькими фоновыми потоками, но LLM-запросы должны быть последовательными.

## 5. Планируемая техническая архитектура

Серверная часть приложения реализуется как модульный монолит и, за исключением Ollama, обязательно развёртывается единым Docker Compose-проектом:

- reverse proxy (Caddy или Nginx): публичный TLS и проверка mTLS;
- backend API: Python 3, планируемый веб-фреймворк — FastAPI;
- фоновый worker: синхронизация источников переписки, анализ, ранжирование, напоминания;
- PostgreSQL: события переписки, цепочки/чаты/встречи, задачи, планы, устройства и журнал обработки;
- изолированный обработчик вложений;
- Android-приложение: Kotlin, Jetpack Compose, Room;
- Firebase Cloud Messaging: только технические push-сигналы.

Ollama остаётся отдельной внешней локальной зависимостью. Её URL задаётся в веб-панели, а доступ разрешается только со стороны backend/worker. Redis, RabbitMQ, Kubernetes и микросервисы для первой версии не требуются. Очередь фоновых заданий можно реализовать на PostgreSQL.

Зафиксированный backend-стек первой версии: Python 3.13.7, FastAPI, SQLAlchemy, Alembic и PostgreSQL. Зафиксированный Android-стек: Kotlin 2.4.20, Jetpack Compose, Room, min SDK 26 и target SDK 36.

## 6. Модель конфигурации

- Эксплуатационные настройки сервера хранятся в таблице `system_settings` PostgreSQL.
- Подключения к IMAP, Exchange и коммуникационным платформам хранятся в таблице `communication_sources`.
- Пароли адаптеров и Firebase service account шифруются AES-GCM перед записью в БД.
- Веб-панель и административный API доступны только через общий HTTPS/mTLS-шлюз.
- Backend и worker перечитывают актуальные настройки из БД без пересборки контейнеров; worker применяет изменения со следующего цикла.
- Внешние загрузчики публикуют heartbeat, ошибку и числовые метрики через mTLS API; просроченный heartbeat получает состояние `STALE`.
- Android показывает общий цветовой индикатор состояния на каждом экране и отдельную таблицу загрузчиков, Ollama, очередей обработки, worker и семафора Ollama.
- В `.env` остаются только параметры начального запуска: соединение с PostgreSQL, пути к master key, данным и TLS/mTLS-материалам, а также публичное имя Caddy.
- Настройка TLS/mTLS не переносится в БД, поскольку она нужна reverse proxy до запуска API.

## 7. Предварительный поток обработки

1. Адаптер источника получает новое письмо, сообщение, изменение чата или расшифровку встречи.
2. Сервер преобразует данные источника в единое событие переписки и нормализует текст, метаданные, участников и вложения.
3. Выполняется дедупликация и привязка к почтовой цепочке, чату или встрече.
4. Для почты удаляются подписи и повторные цитаты; для расшифровок сохраняются говорящие и временные метки.
5. Поддерживаемые вложения безопасно преобразуются в ограниченное текстовое представление.
6. Правила определяют участников, идентичность пользователя, адресатов/говорящих и первичные признаки поручения.
7. Qwen одновременно возвращает задачи и структурированный смысловой индекс события и цепочки:
   резюме, категории, ключевые слова, сущности, решения и договорённости.
8. Сервер валидирует результат и решает: создать задачу либо запросить подтверждение.
9. PostgreSQL сохраняет задачу, происхождение, доказательный фрагмент, версию модели, результат
   анализа и смысловой индекс; старые события доиндексируются worker'ом в фоне.
10. План и рейтинг пересчитываются.
11. При необходимости сервер отправляет обезличенный FCM-сигнал.
12. Android-приложение получает данные через mTLS.
