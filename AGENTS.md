# Правила проекта

## Версии при изменении кода

При законченном наборе изменений кода повышайте версию выпуска для Docker и
Windows только если корневой файл `version` ещё не изменён относительно `HEAD`.
Учитывайте как staged, так и unstaged изменения. Если файл уже изменён,
используйте указанную в нём версию без повторного повышения и синхронизируйте
с ней остальные файлы версий. По умолчанию повышайте PATCH; для нового
несовместимого контракта выбирайте соответствующий SemVer.
Не повышайте версию отдельно для каждого файла или промежуточного исправления.

- Единая версия Docker и Windows хранится в корневом файле `version`.
- Одновременно обновляйте `backend/pyproject.toml` и значение `AppVersion`
  по умолчанию в `windows/installer.iss`.
- Docker-образы собирайте с `APP_VERSION` из `version` и отдельным тегом этой
  версии. Для компонентов сохраняйте суффиксы `-document-parser`, `-cert-init`
  и другие принятые в проекте суффиксы. Не ограничивайтесь тегами `local`,
  `latest` или датой исправления. Стабильные теги могут оставаться псевдонимами.
- Windows-сборка должна получать ту же версию из `version`, как уже делает
  `windows/build.ps1`. Не публикуйте другой код под ранее выпущенной версией.
- macOS DMG использует ту же версию из `version`: синхронизируйте
  `macos/package.json` и `macos/package-lock.json`. Сборка — `python3 macos/build.py`;
  DMG должен содержать arm64 и x86_64 для Electron и всех серверных компонентов.
- При изменении Android-кода также повышайте `versionCode` и `versionName`
  в `android/app/build.gradle.kts`.
- Перед завершением проверяйте согласованность версий. В отчёте различайте
  обновление исходников, сборку, публикацию и фактическое обновление прода;
  не заявляйте о публикации или установке без проверки результата.

## Системные исправления LLM в релизе

Если новая версия включает `issue_id` в
`backend/internal/server/llm_fix_manifest.json`, после сборки и фактической
установки серверного релиза зарегистрируйте новые исправления в CRM шлюза через
`../ai-secretary-gateway/tools/register_release.py`. Передайте манифест,
корневой `version`, идентификатор установленного артефакта с SHA-256, результаты
проверки и действующий операторский mTLS-сертификат. Скрипт сверяет `fix_id`,
`issue_id` и область исправления с CRM и регистрирует только исправления с
`fixed_version` текущего выпуска. Gateway сам закрывает связанные обращения;
отдельно менять их статусы не нужно. После регистрации проверьте в CRM состояния
проблем и обращений. Не регистрируйте запланированный, но не установленный релиз.
